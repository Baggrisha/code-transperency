# Пользовательский путь: проверка исполнения контракта

## Цель

Специалист собирает документы по контракту, проверяет распознанные данные и получает объяснимые сигналы о возможных расхождениях. Решение по каждому сигналу принимает человек.

## Основной сценарий

### 1. Открыть реестр проверок

Пользователь попадает на страницу «Все проверки». Здесь доступны список дел, поиск по номеру или названию контракта, фильтр по статусу и счётчики. Можно открыть существующую проверку или создать новую.

### 2. Создать проверку

Пользователь нажимает «Новая проверка», вводит наименование, при необходимости — номер контракта и описание. После создания открывается рабочая область проверки с разделом загрузки документов.

### 3. Загрузить документы

В разделе «Документы» пользователь выбирает или перетаскивает файлы: контракт, спецификацию, накладные, документы о приёмке и дополнительные соглашения. При необходимости указывает тип документа и номер контракта, затем запускает загрузку. Загруженные документы появляются в комплекте; их можно открыть, изменить тип или исключить из сверки.

### 4. Проверить распознанные данные

В разделе «Распознавание» пользователь просматривает извлечённые реквизиты и товарные строки, при необходимости открывает исходный документ и исправляет ошибки. Проверенные поля и строки подтверждаются явно. Для сохранения изменений указываются проверяющий и комментарий.

### 5. Сопоставить документы и запустить сверку

В разделе «Сопоставление» пользователь задаёт дату среза и параметры проверки, просматривает связи позиций и при необходимости подтверждает ручное сопоставление. Затем запускает сверку комплекта. Если документов или данных недостаточно, система показывает соответствующие замечания; отсутствие документа в комплекте само по себе не доказывает его отсутствие у сторон.

### 6. Изучить результаты

В разделе «Результаты» отображаются состояние проверки, сводка по количествам и карточки сигналов. Для каждого расхождения доступны описание, ожидаемое и фактическое значения, правило проверки и фрагменты исходных данных. При необходимости пользователь открывает документ или его реквизиты.

### 7. Принять решение по сигналу

Пользователь выбирает статус рассмотрения: «Требует рассмотрения», «Расхождение подтверждено», «Устранено» или «Сигнал отклонён». Он указывает проверяющего и комментарий, затем сохраняет решение. Статус и комментарий отображаются в карточке и сохраняются в истории.

### 8. Вернуться к проверке или выгрузить результат

Пользователь может вернуться в реестр, открыть историю действий дела или историю запусков, просмотреть сохранённый результат и выгрузить отчёт или данные в доступном формате. Если документы или их реквизиты изменились, пользователь повторно запускает сверку: прежний результат сохраняется в истории и помечается как устаревший.

## Альтернативный вход: готовая проверка

На странице «Все проверки» пользователь может раскрыть «Готовые проверки», выбрать пример и нажать «Открыть проверку». Система создаёт дело на синтетических данных и выполняет сверку. Например, T02 показывает расхождение между количеством в акте и накладной.

## Важно

Основной интерфейс работает с серверным API и хранилищем. Отдельный автономный прототип `/prototype` предназначен для просмотра сценария: он не выполняет распознавание и реальную сверку загруженных файлов.
