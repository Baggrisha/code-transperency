# Техническое описание для паспорта проекта

## Цель

Разработан локальный демонстрационный модуль «Контроль исполнения» для сопоставления документов поставки и приёмки с условиями одного контракта. Его задача – показать документальные расхождения, объяснить расчёт и сохранить решение специалиста. Требования основаны на разделах 7–10 исследования «финал финал(1).pdf» и согласованном перечне задач разработки. Проверяемая гипотеза проекта состоит в том, что такая сверка может сократить ручную работу без потери возможности восстановить основания вывода. Измерение этого эффекта требует пользовательских испытаний.

## Реализация

Подготовлено работающее приложение с HTTP API, командной строкой и локальной демонстрационной панелью. В нём реализованы загрузка документов, извлечение реквизитов и табличных строк, нормализация значений, сопоставление товаров, проверка количества, цены, суммы строки и срока поставки. Система учитывает несколько накладных, исправленные и отменённые документы, повторные загрузки, дополнительные соглашения и смену спецификации. Для спорных данных предусмотрены исправление извлечения, ручная связь позиций, статусы рассмотрения и комментарии.

Результат проверки содержит ожидаемые и обнаруженные значения, объяснение применённого правила и ссылки на исходные документы. Количество по накладным и количество по актам учитываются отдельно. Например, две накладные на восемь и две единицы образуют поставку десяти единиц. Акт на десять не увеличивает поставку ещё на десять. Если акт превышает объём загруженных накладных, система предлагает проверить дополнительные документы и корректировки; причина расхождения не объявляется установленной автоматически.

## Архитектура

Основной стек – Python 3.11+, FastAPI, Pydantic, Uvicorn и SQLite. Программные модули разделяют модель данных, извлечение, нормализацию, правила сверки, хранение и экспорт. Для PDF применяется pdfplumber, для DOCX – python-docx, для изображений – Pillow. Необязательное распознавание сканов выполняется локальными Tesseract и Poppler. Внешняя языковая модель не используется; приложение не требует ключа API и не отправляет документы в сторонний сервис обработки.

SQLite хранит дела, текущие структуры документов, предыдущие версии извлечения, снимки запусков, решения по сигналам и журнал событий. Исходные файлы сохраняются отдельно. Исправление данных требует номера ожидаемой версии, поэтому одновременная правка не затирает чужое изменение молча. После изменения комплекта старый результат сохраняется и помечается как относящийся к прежнему состоянию. Для интеграции с интерфейсом доступны маршруты загрузки, сверки, исправления, истории и экспорта JSON, CSV, HTML и PDF; журнал запусков доступен через `GET /api/runs`.

## Данные

Для демонстрации подготовлены синтетические документы и двенадцать проверочных комплектов. Они не выдаются за реальные государственные закупки. Поддерживаются JSON, TXT, CSV, TSV, табличные DOCX и PDF, изображения и сканированные PDF при наличии OCR. Для каждого извлечённого значения сохраняется доступный источник: файл, страница, строка, поле и фрагмент. Там, где номер страницы неизвестен, он не добавляется.

Пропущенные значения сохраняются неизвестными. Числа с неоднозначным распознаванием не заменяются догадкой. Оценки уверенности используются для направления данных на проверку и не означают измеренную точность распознавания. Результат OCR требует проверки по оригиналу; отдельные похожие идентификаторы могут быть автоматически связаны по правилу ниже без изменения исходного текста. Другие неподтверждённые поля продолжают блокировать соответствующие сравнения. Отсутствие русского языкового пакета возвращает явное предупреждение и неполный документ.

## Алгоритм

Обработка начинается с проверки файлов и исключения повторов. Затем выбираются действующие документы и строится история условий контракта. Исправление связывается с исходной версией через явную ссылку. Дополнительное соглашение применяется при наличии основания, даты вступления в силу и подтверждения специалистом. Оно может задать новый срок либо полную новую спецификацию. Количество сравнивается с редакцией на дату среза, а цена и срок поставки – с условиями соответствующего периода.

Позиции связываются по подтверждённой ручной связи, номеру позиции, уникальному артикулу или точному уникальному названию. Единственный похожий артикул или номер договора может быть связан автоматически, если различия ограничены похожими символами и не превышают трёх неоднозначных замен; одинаково выглядящие буквы кириллицы и латиницы в лимит не входят. Несколько кандидатов, более трёх таких замен и конфликт идентификаторов требуют уточнения. Похожие названия дают предложение для проверки. Неизвестный коэффициент перевода упаковок и низкая уверенность иных значений блокируют затронутый расчёт.

Денежные операции выполняются через Decimal. Цена приводится к единому виду с учётом скидки, НДС и единицы измерения. Неизвестный налоговый базис или разные валюты не сравниваются автоматически. Частичная поставка сама по себе не создаёт сигнал о недопоставке: для проверки завершённого объёма пользователь явно отмечает комплект завершённым. Система отдельно проверяет превышение приёмки над накладными и документального объёма над спецификацией.

## Апробация и воспроизводимость

Реализованы сценарии T01–T12 из исходного исследования: полное совпадение, неполный комплект, частичные поставки, новая спецификация, повторная загрузка, разные названия при одном артикуле, разные единицы, исправление накладной, пропуск данных, НДС и скидка, перенос срока и неоднозначный скан. В T12 вручную задан неоднозначный результат OCR для проверки реакции правил; качество распознавания сканов этим сценарием не измеряется. Дополнительные регрессионные проверки охватывают крайние случаи правил, чтение синтетических файлов PDF/DOCX и работу API. Результат зависит от проверенной версии правил и среды; актуальные результаты получают повторным запуском тестов.

Дата среза задаётся явно. Расчёт использует фиксированную версию правил и контекст Decimal, вход и результат получают SHA-256. Сохранённый запрос позволяет повторить проверку. Время записи в базу и идентификатор запуска не влияют на арифметический результат. Прохождение синтетических сценариев подтверждает выполнение проверенных условий, но не позволяет заявлять отраслевую точность или экономический эффект.

## Ограничения

Версия предназначена для локального пилота. Она не интегрирована с государственными реестрами, не проверяет электронную подпись и юридическую действительность соглашений, не принимает решения о приёмке и оплате. Накопительные акты требуют разбиения; произвольные положения договора не переводятся автоматически в правила. Для реальных документов необходимо проверить извлечение и полноту комплекта. Производственные роли, SSO и распределённая очередь обработки не реализованы. Следующий этап – согласованный обезличенный набор, независимая разметка специалистами и пользовательское сравнение ручной проверки с работой через модуль.
