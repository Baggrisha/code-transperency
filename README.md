# Контроль исполнения

Рабочий локальный прототип сверки документов одного контракта. Проверяет контракт или связанную спецификацию, накладные и акты приёмки, учитывает исправления и дополнительные соглашения. Сигнал содержит значения, правило расчёта и ссылки на исходные фрагменты. Решение специалиста сохраняется отдельно от результата алгоритма.

В комплекте: Python-сервис, демонстрационная панель, HTTP API, CLI, синтетические документы, 12 приёмочных сценариев, регрессии и техническое описание для паспорта проекта. Версия приложения `0.1.0`, схема `1.0`, правила `rules-1.2.0`.

## Быстрый запуск

### macOS (Apple Silicon и Intel)

```bash
xcode-select --install                 # один раз, если git ещё не установлен
brew install python@3.13               # если python3 --version ниже 3.11
git clone https://github.com/Baggrisha/code-transperency.git
cd code-transperency
./scripts/setup.sh                     # создаёт .venv и ставит зависимости из requirements-lock.txt
./scripts/start.sh                     # http://127.0.0.1:8000, порт можно передать: ./scripts/start.sh 8001
```

Для сканов (PNG/JPG/TIFF и PDF без текстового слоя) дополнительно: `brew install tesseract tesseract-lang poppler`. Текстовые PDF, DOCX, TXT, CSV и JSON работают без этого. Все зависимости из `requirements-lock.txt` имеют готовые колёса `macosx arm64` для Python 3.12–3.14, компилятор не нужен. В macOS нет команды `python` вне виртуального окружения — используйте `python3` или скрипты выше. Если порт 8000 занят, запустите на другом: `./scripts/start.sh 8001`.

Данные лежат в `data/` рядом с проектом (`kontrol.sqlite3` и `files/`) и сохраняются между перезапусками. Каталог можно перенести или указать другой через `KONTROL_DATA_DIR`: пути к исходным файлам хранятся относительно него.

### Вручную (Linux, Windows, macOS)

Проверено на Python 3.12.14 и 3.13. Минимальная версия Python – 3.11. Откройте терминал в папке репозитория.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-lock.txt
python -m uvicorn kontrol.api:app --host 127.0.0.1 --port 8000
```

В Windows вместо `source .venv/bin/activate`:

```powershell
.venv\Scripts\Activate.ps1
```

Откройте [панель проверки](http://127.0.0.1:8000) или [интерактивную документацию API](http://127.0.0.1:8000/docs). Панель обслуживается тем же сервером; отдельный Node.js-сервер не нужен. Все файлы, шрифты и код панели находятся локально, CDN не используется.

Для запуска только сервиса достаточно `requirements.txt`; полный `requirements-lock.txt` фиксирует также зависимости записанного тестового прогона. `requirements-dev.txt` содержит прямые зависимости разработки. После установки приложение обрабатывает документы локально, без ключей LLM API.

## Проверка за несколько минут

Откройте стартовую страницу, выберите пример **T02 · Акт и комплект поставки расходятся** и нажмите «Открыть пример». Приложение создаст отдельное дело из синтетических данных и выполнит сверку. В накладной будет 8 единиц, в акте – 10. Карточка покажет расхождение, источники и предложение проверить комплект.

Пример **T03** содержит две накладные – 8 и 2. Сумма поставки составит 10, и ложного сигнала о недопоставке не будет. Все 12 примеров доступны в том же списке.

Чтобы проверить именно извлечение из файлов, создайте новое дело и загрузите вместе:

- `examples/contract.txt`;
- `examples/delivery_8.csv`;
- `examples/delivery_2.csv`;
- `examples/acceptance.txt`.

Установите дату среза `2026-10-31` и выполните сверку. Ожидаемый результат – 10 предусмотрено, 10 поставлено, 10 принято, сигналов нет. Если не загружать `delivery_2.csv`, появляется вопрос о разнице между актом и накладными. Эти файлы содержат реквизиты и таблицы, а не готовый JSON результата. Фактический результат этого прогона сохранён в `reports/import_examples_result.json`.

Через «Реквизиты» можно исправить номер, дату и значения строк, указать отмену или замену документа. Нужны имя проверяющего и комментарий. Галочка подтверждения строки отмечает проверенные значения; пункт «Замечания извлечения разобраны» подтверждает рассмотрение реквизитов. После изменения повторите сверку: старый результат остаётся в истории и помечается как устаревший.

Панель служит для демонстрации основного сценария. Краткое руководство для фронтенда с примерами запросов и ответов: `docs/frontend-api.md`. Все поля расширенной схемы, включая характеристики, коэффициенты перевода и сложные связи документов, доступны в API. Для собственной фронтенд-реализации используйте `docs/openapi.json` и маршруты ниже.

## Что проверяет алгоритм

| Область | Поведение |
| --- | --- |
| Повторы | Один файл или документ не удваивает поставку и приёмку |
| Исправления | Явная цепочка `supersedes`; конфликтующие редакции требуют выбора |
| Изменения контракта | Подтверждённое соглашение, дата действия, основание, новая спецификация и/или срок |
| Связи товаров | Позиция контракта, уникальный артикул, точное название, ручная связь |
| Похожие названия | Предложение с кандидатами; подтверждение остаётся за человеком |
| Частичная поставка | Накладные суммируются отдельно от актов; незавершённый остаток не объявляется недопоставкой |
| Связанные документы | Проверяются отдельные связанные группы актов и накладных |
| Единицы | Нормализация и метрические переводы; упаковке нужен явный коэффициент |
| Стоимость | Decimal, налоговый базис, скидка, валюта, сумма строки, историческая цена |
| Срок | Условия на дату накладной; источник срока сохраняется при последующих изменениях |
| Неизвестные значения | `null`, предупреждение и ограничение расчёта; число не подставляется догадкой |
| Рассмотрение | Статус, комментарий, автор, история; расчётный снимок не переписывается |

Номера договоров и артикулы, которые различаются только визуально похожими символами (`0`/`O`/`О`, `1`/`I`/`l`, латиница/кириллица), автоматически сопоставляются при единственном варианте. Цена, количество и остальные реквизиты сверяются отдельно; их расхождения не скрываются. Исходное значение сохраняется, автоматическая связь и её основание видны в результатах и отчёте. При нескольких возможных вариантах или конфликте идентификаторов требуется ручная проверка. Такое сопоставление не доказывает подлинность документов: разные идентификаторы могут выглядеть одинаково.

`approved=true` у соглашения означает подтверждение его применения пользователем. Юридическая действительность не устанавливается алгоритмом. `amount` в схеме означает **итоговую сумму строки с НДС после скидки**. Укажите эту основу явно при подготовке структуры: сумма без налога должна быть приведена к ней человеком или адаптером конкретного формата.

## Файлы и OCR

Поддержаны JSON одного документа, TXT, CSV, TSV, табличные DOCX и PDF. PNG, JPEG, одностраничный TIFF и сканированные PDF используют локальные Tesseract и Poppler. Для русских сканов нужны языковые данные `rus`; по умолчанию вызывается `rus+eng`.

Для Ubuntu/Debian дополнительные системные зависимости устанавливаются так:

```bash
sudo apt-get update
sudo apt-get install tesseract-ocr tesseract-ocr-rus tesseract-ocr-eng poppler-utils
```

Для Windows/macOS установите Tesseract с русским языком и Poppler, добавив `tesseract` и `pdftoppm` в PATH. Проверка языка: `tesseract --list-langs`. Извлечение из текста PDF и DOCX не требует Tesseract.

Если русского языка нет, система возвращает `OCR_LANGUAGE_MISSING`, а не выдаёт распознавание английской моделью за корректный результат. В записанном тестовом окружении проверен реальный английский OCR и обработка отсутствующего русского пакета; точность русского OCR здесь не измерялась. Все результаты OCR требуют подтверждения перед автоматическим сравнением.

Форматы реквизитов, таблиц, метаданных и ограничения описаны в `docs/extraction.md`. Для неизвестного шаблона укажите тип и номер контракта в параметрах загрузки либо подготовьте структуру после просмотра оригинала. Парсер не обещает понимать любой произвольный договор.

## Командная строка

```bash
python -m kontrol demo T02 -o reports/demo-T02.json --html reports/demo-T02.html
python -m kontrol check examples/complete_request.json -o reports/full-check.json
python -m kontrol extract examples/delivery_8.csv -o reports/extracted-delivery.json
```

`extract` возвращает документ, текст и предупреждения. `check` принимает `CheckRequest` с массивом `documents` и явным `as_of`. Ошибки входа завершают CLI кодом 2. Наличие проверочного сигнала – нормальный результат выполнения, а не авария программы.

## Интеграция с интерфейсом

Создание дела:

```javascript
const dossier = await fetch('/api/cases', {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({title: 'Поставка мебели'})
}).then(r => r.json());

const upload = new FormData();
upload.append('file', file);
const document = await fetch(`/api/cases/${dossier.id}/documents`, {
  method: 'POST', body: upload
}).then(r => r.json());

const run = await fetch(`/api/cases/${dossier.id}/runs`, {
  method: 'POST',
  headers: {'Content-Type': 'application/json'},
  body: JSON.stringify({as_of: '2026-10-31', delivery_complete: false})
}).then(r => r.json());
```

В рабочем интерфейсе проверяйте HTTP-статус перед использованием тела ответа; примеры показывают успешный путь. Десятичные значения API возвращает строками, чтобы не терять точность при JSON-передаче. Не пересчитывайте деньги через JavaScript `Number`: отрисовывайте серверные значения или используйте десятичную библиотеку.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/cases` | Список проверок |
| `GET /api/cases/{id}` | Комплект документов и запуски |
| `POST /api/cases/{id}/documents` | Multipart-загрузка с извлечением |
| `POST /api/cases/{id}/structured` | Один структурированный документ |
| `PUT /api/cases/{id}/documents/{document_id}` | Исправление с `expected_revision`, `reviewer`, `comment` и явным подтверждением полей |
| `GET /api/cases/{id}/documents/{document_id}/history` | История извлечения и исправлений |
| `GET /api/cases/{id}/documents/{document_id}/file` | Исходный файл, если загружен |
| `POST /api/cases/{id}/runs` | Сверка сохранённого дела |
| `POST /api/check` | Сверка массива документов без записи в БД |
| `POST /api/extract` | Извлечение файла без сохранения |
| `GET /api/runs` | Журнал проверок: статус, число сигналов, актуальность; фильтры `case_id`, `status`, `limit`, `offset` |
| `GET /api/runs/{id}` | Исходный запрос, результат, решения, `latest_reviews`, `prior_reviews` и признак `stale` |
| `POST /api/runs/{id}/signals/{signal_id}/reviews` | Новая запись рассмотрения |
| `GET /api/runs/{id}/export?format=json` | Полный снимок с решениями; также `csv`, `html` и `pdf` (кириллица, шрифт DejaVu Sans в `kontrol/fonts`) |
| `GET /api/cases/{id}/events` | Журнал действий; фильтры `action`, `since`, `after_sequence`, `limit` |

Результат имеет статус `ok`, `needs_review` или `incomplete`. `ok` означает отсутствие сигнала в пределах выполненных проверок, а не доказанную полноту реальной закупки. Ручные решения `confirmed`, `resolved`, `dismissed` и `needs_review` хранятся отдельными записями. Последнее решение можно получить из последней записи `reviews` с соответствующим `signal_id`; исходный `result.signals[].status` не изменяется.

Загрузка поддерживает поля `document_type`, `contract_id` и строку `metadata` с JSON-объектом разрешённых реквизитов. Исправленный официальный документ загружается с новым `id` и ссылкой `supersedes`. Исправление распознанной цифры в том же файле выполняется через PUT и не подменяет деловую редакцию документа.

При исправлении PUT принимает `confirmed_fields` — список проверенных полей документа, и `confirmed_items` — объект `{ "line_id": ["quantity", "unit_price"] }` с подтверждёнными полями строк. При добавлении, удалении или перестановке позиций отдельно подтверждается поле документа `items`; новые значения также подтверждаются по отдельности. Изменение без подтверждения сохраняется с нулевой уверенностью и требует проверки. Имя проверяющего и комментарий обязательны, предыдущая редакция остаётся в истории. Неизвестные поля и ссылки на отсутствующие строки отклоняются.

Ошибочные ключи оценок уверенности, которых нет в модели документа или позиции, можно явно удалить через `discarded_confidence_fields` и `discarded_item_confidence`. Разрешается удалять только ключи из сохранённой версии; операция записывается в историю с автором и комментарием. Оценки существующих и служебных полей так удалить нельзя.

## Настройки

| Переменная | Назначение |
| --- | --- |
| `KONTROL_DATA_DIR` | Каталог SQLite и исходников; по умолчанию `data` рядом с проектом |
| `KONTROL_API_TOKEN` | Необязательный общий Bearer-токен для `/api/*` |
| `KONTROL_CORS_ORIGINS` | Разрешённые origin через запятую. Не задана — разрешены `localhost`/`127.0.0.1` на любом порту; пустая строка — CORS выключен |

Если задан токен, передавайте `Authorization: Bearer ...`. В демонстрационной панели есть кнопка «Доступ», в Swagger – Authorize. Токен панели хранится только в sessionStorage текущей вкладки. Фронтенд, запущенный локально на другом порту (например, Vite на `5173`), работает без настройки. Для другого адреса задайте, например, `KONTROL_CORS_ORIGINS=https://demo.example`.

Файлы до 20 МиБ принимаются API; остальные лимиты описаны в документации извлечения. Долгая обработка выполняется в рабочем потоке; сервис предназначен для локального пилота с одним процессом Uvicorn.

## Проверка реализации

```bash
python -m unittest discover -s tests -v
python scripts/run_cases.py --output reports/acceptance.json
python scripts/export_openapi.py   # после изменения API; тест сверяет docs/openapi.json с приложением
```

Файл `reports/acceptance.json` содержит сохранённый протокол T01–T12 с версией правил и хешем набора; при изменении кода запустите его повторно. `reports/unittest.txt` относится к предыдущей версии правил. Ключевые ожидания зафиксированы в `tests/acceptance_spec.md`, а эталон не вычисляется производственным кодом.

T12 содержит вручную заданный синтетический результат неоднозначного OCR и проверяет реакцию алгоритма. Тесты `test_extraction.py` создают PDF/DOCX, читают их и запускают английский Tesseract при наличии. Эти результаты нельзя называть точностью на реальных закупках или экономией рабочего времени. Для панели предусмотрен прогон формирования экранов в Node VM; он не заменяет браузерную проверку.

Для воспроизведения расчёта сохраняйте `request` из отчёта, версию правил и зависимости. Для воспроизведения извлечения также сохраняйте исходный файл и версии Tesseract/Poppler. `reports/build_manifest.json` относится к предыдущей версии и не подтверждает состав текущей рабочей копии. Даты событий и UUID дел не входят в детерминированный результат ядра.

## Границы версии

Накопительные акты `cumulative` автоматически не суммируются: нужен подтверждённый разбор по поставкам. Допсоглашение задаёт полную замену спецификации и/или срок. Возвраты отрицательными количествами, произвольные условия свободного текста и автоматическая проверка электронной подписи не реализованы. Дата поставки берётся из документа; фактическую передачу товаров алгоритм не устанавливает.

История запусков воспроизводит сохранённые снимки. Установка более раннего `as_of` в изменённом сегодняшнем комплекте не восстанавливает неизвестный прошлый статус отмены. Для такого исследования нужен сохранённый снимок того периода.

Русский OCR, пользовательская эффективность и полевое качество на чужих шаблонах требуют отдельной апробации. Интеграций с госреестрами, производственных учётных записей/SSO и распределённой очереди здесь нет. Подключение к интерфейсу команды выполняется через готовый HTTP API.

## Источники проектирования

Требования: предоставленное исследование, разделы 7–10, страницы 8–12; перечень 13 задач пользователя. Актуальные технические контракты сверялись с [документацией загрузки файлов FastAPI](https://fastapi.tiangolo.com/tutorial/request-files/), [документацией сериализации Pydantic](https://docs.pydantic.dev/latest/concepts/serialization/), [руководством Tesseract](https://github.com/tesseract-ocr/tessdoc/blob/main/Installation.md) и [справкой Decimal](https://docs.python.org/3.12/library/decimal.html). Детали конкретной реализации определяются кодом и схемой этого проекта.
